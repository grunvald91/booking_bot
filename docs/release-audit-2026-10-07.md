Важные критерии приёмки:

- [ ] Продавец поддерживает фиксированные услуги/допуслуги и описанные в инструкции
  сценарии аренды. Сложные групповые/временные тарифы, абонементы, ночные окна и
  аренда с юридическими согласиями корректно направляются в действующую форму
  или оператору. Не считать первую версию поддержкой всех сценариев сервиса.
- [ ] После сообщения клиента об оплате `prepayment_sent` **останавливает автоотмену**.
  Владелец не обязан ответить за оставшиеся клиентские 10 минут.
- [ ] «Да» подтверждает фактическое поступление и весь визит. «Нет» возвращает
  ожидание и даёт новое десятиминутное окно исправления. Клиента не просят повторно
  платить, если перевод уже списан. Отмена не выполняет автоматический возврат денег.
- [ ] Проверены веб → бот и бот → веб: общий статус, версии, чеки и решения.
  Старые чеки, которые были только пересланы в Telegram, не обещаются в веб-архиве.
- [ ] Объединение не теряет бизнесы, совладение, клиентские брони и абонементы;
  гостевая запись по телефону не получает доступ к объединённому владельцу.
  Telegram с другой подтверждённой почтой и два аккаунта с подписками получают
  понятное направление оператору, без самостоятельной замены прав.

## Собственный почтовый сервер: уже есть, но требуется приёмка доставки

Это **не задача построить новый сервер или подключить платного поставщика**.

- [Успешный исторический аудит](https://github.com/grunvald91/booking_bot/actions/runs/37421133374)
  подтвердил активные Postfix/OpenDKIM и `dkim_signature_present=yes`.
  Есть [успешный шаг настройки](https://github.com/grunvald91/booking_bot/actions/runs/37421986431).
- Сейчас `mail.servgo.ru` разрешается в `155.212.162.47`. Публичная DNS-проверка
  через Google DNS не нашла MX/TXT(SPF) для `servgo.ru`, DKIM
  `s202610._domainkey.servgo.ru` и DMARC `_dmarc.servgo.ru`. PTR по-прежнему
  указывает на имя провайдера. Внешнее соединение с `mail.servgo.ru:587` отклоняется.
- Закрытый внешний 587 **не доказывает отказ локальной отправки**: предыдущий
  аудит описывает локальный SMTP на порту 25. Реальные настройки процесса API
  нужно сверить с существующей схемой, не подставлять предположительный endpoint.

Приёмка:

- [ ] API и бот используют нужный существующий SMTP и корректный sender.
- [ ] Проверены DNS/SPF/DKIM/DMARC/PTR и доступность нужного SMTP-маршрута.
- [ ] Код регистрации/восстановления приходит на внешнюю тестовую почту вовремя,
  заголовки подтверждают проверку подписи; SMTP acceptance не выдаётся за доставку.
- [ ] Обычный вход по паролю не отправляет письмо. Письмо о создании записи
  не дублируется. Ошибка доставки не подтверждает email и не ломает бронь.

## Порядок выпуска и общая приёмка

1. **Сверить реальные файлы и службы.** Сохранить серверные версии/хеши и базу.
   Исходники ServGo отличаются от GitHub; сохранить существующий `servgo_auth`,
   Telegram transport и production конфигурацию. Не заливать весь репозиторий.
2. **Собрать итоговую версию.** Разрешить пересечения указанных веток и вариантов
   промо. Проверить migrations, backend, frontend и интеграционные сценарии.
   Текущие 108 тестов ServGo и 4 subtests прошли локально; это не заменяет приёмку
   на сервере. CI PR №34 не запустил команды — runner ID 0, причина неизвестна.
3. **Миграции до новых процессов ServGo:**
   `add_sales_conversations.sql`, `add_sales_agent_settings.sql`,
   `add_prepayment_requested_at.sql`, `add_email_auth_and_payment_review.sql`,
   `add_telegram_account_link.sql`. Это новые таблицы/колонка; отдельно проверить
   существующие prerequisite-поля пользователя, брони и правил бизнеса.
   Для комментариев Growth OS — Alembic **0005** после существующей 0004.
4. **Конфигурация:** ClaudeHub BASE_URL/MODEL/API_FORMAT/KEY; собственный SMTP;
   сильные разные `JWT_SECRET`/`SERVGO_EMAIL_AUTH_SECRET`; согласованные
   `BOT_USERNAME`/`BOT_TOKEN`; интеграционный токен ServGo, allowlist бизнесов,
   адрес API и отдельный пароль владельца Growth OS. Для комментариев — существующий
   прокси. Не передавать секреты в браузер, отчёт или LLM.
5. **Загрузить согласованные компоненты:** файлы из приложенного manifest,
   новый React build целиком с актуальными asset names и service worker.
   Перезапустить API ServGo и `booking-bot`; в Growth OS пересобрать/recreate
   API/worker и, для G3, Telegram-контроллер. У G2 новая зависимость `markdown-it-py`.
   Сохранить persistent profile/integration volumes, включая ключ шифрования.
6. **Проверить:** health обеих систем, маршруты и доступы, мобильный/desktop UI,
   свежую сборку после перезагрузки/PWA, отсутствие ошибок процессов. Приёмку
   брони/предоплаты проводить в выделенном demo-бизнесе, проверять и обычный бот.
7. **Только после исправной работы новых компонентов** рассмотреть
   `activate_rental_prepayment_windows.sql`: она переводит существующие согласованные
   положительные депозиты аренды в ожидание и запускает реальное 10-минутное окно.
   Это не подготовительная DDL-миграция; заранее проверить список затрагиваемых броней.
8. **Зафиксировать выпуск:** реальный SHA/manifest/хеши, время, миграции, список
   успешных сценариев и оставшиеся отклонения. После этого этот список можно закрывать.

Откат — согласованные прежние файлы и процессы; новые таблицы/чеки/историю не
удалять. После уже выполненного объединения сохранить поддержку account aliases
и исключение merged users из гостевого поиска. Сохранить совместимый expiry helper,
пока существуют запущенные платёжные окна. Не отменять изменения владельцев или
созданные клиентские записи массовым SQL ради возврата предыдущего интерфейса.
