# ServGo — план подготовки к масштабированию

**Версия:** 2.0 (проверенная), 30 октября 2026  
**Статус:** план реализации; изменения в исходный код по этому документу ещё не внесены.  
**Область:** [BookingBot](https://github.com/grunvald91/booking_bot), [AI Growth OS](https://github.com/grunvald91/Ai_growth_os), [SMENA](https://github.com/grunvald91/SMENA), будущие общие CRM/MCP-интеграции.  
**Принцип:** исправить корректность и безопасность → оптимизировать базу → обеспечить надёжные фоновые операции → безопасно распараллелить AI → измерить пределы → масштабировать инфраструктуру по необходимости.

> Важно: выводы основаны на исходниках веток main. Конфигурация production, применённые миграции, размеры таблиц и фактическая нагрузка должны быть проверены отдельно. Цифры «10–500 виртуальных пользователей» ниже — сценарии испытаний, а не подтверждённая пропускная способность.

## 1. Результат и критерии качества

Цель — рост числа компаний, сотрудников и клиентов без:
- доступа к данным чужого бизнеса;
- ошибочно свободных интервалов и двойного бронирования;
- потерянных конкурентных изменений;
- бесконтрольных повторов отправки уведомлений и платных вызовов;
- блокирования Booking API длительным AI-рендером;
- неуправляемого роста SQL-соединений, времени запросов и затрат.

Готовность определяется **измерением**, а не числом зарегистрированных пользователей. Для целевого профиля нагрузки заранее согласуются RPS, доля операций, p95/p99, error rate, допустимая задержка задач, бюджет AI и требования восстановления.

**Безусловные инварианты:** нельзя читать закрытые данные чужой компании, нельзя успешно дважды занять пересекающийся интервал одного ресурса, нельзя молча перезаписать конкурентное изменение, нельзя без согласования повторить платную операцию с неопределённым результатом.

## 4. Этап 1 — P0: целостность и изоляция BookingBot

**Файлы:** webapp/server.py, слой проверки прав и тесты.

- [ ] Разделить политики public booking / authenticated client / master / administrator / owner / platform operator.
- [ ] Исправить api_analytics_data и api_analytics_schedule: проверить разрешённый business_id перед выборкой.
- [ ] Провести аудит всех HTTP/Telegram/CRM-операций с business_id, booking_id, service_id, employee_id, client_id, subscription_id и вложенными ресурсами.
- [ ] Проверять принадлежность связанных идентификаторов выбранному бизнесу, даже если право пользователя на сам бизнес уже подтверждено.
- [ ] Не закрывать публичную запись авторизацией владельца: публичные действия должны иметь отдельную минимальную политику и ограничения.
- [ ] Проверить владельца нескольких бизнесов и сотрудников с несколькими ролями.

**Приёмка:** чужие приватные данные/мутации недоступны во всех защищённых маршрутах; публичная клиентская запись работает.

### SG-02 — единая модель свободного и занятого слота

**Файлы:** webapp/server.py, database/booking_safety.py, тесты.

- [ ] Удалить рассогласование статусов: использовать централизованный ACTIVE_BOOKING_STATUSES, включая pending_prepayment, prepayment_sent, prepayment_confirmed.
- [ ] Применять occupies_resource и immutable resource_duration_minutes, не полагаться только на текущую Service.duration_minutes.
- [ ] Корректно учитывать дополнительные услуги, несколько услуг подряд, помещения, индивидуальные интервалы мастеров, ночные записи.
- [ ] Исправить подбор «Любой мастер» в клиентском и административном потоке.
- [ ] Проверить принадлежность услуг/мастеров компании в слотовых API.
- [ ] Проверить резерв предоплаты (включая истечение 10 минут), отмену, перенос и подтверждение.
- [ ] Создать тесты «интерфейс свободно ↔ сервер действительно принимает бронь» с контролем реальной гонки при последующем INSERT.

**Приёмка:** алгоритмы отображения и записи используют единые инварианты; занятой ресурс не предлагается как доступный.

### SG-03 — атомарные изменения записей

**Файлы:** database/crud.py, все маршруты изменения статуса/мастера/времени, migrations.

- [ ] Заменить read/check/write Booking.version на атомарный UPDATE с WHERE id = ... AND version = expected_version и version = version + 1.
- [ ] Отсутствие затронутых строк трактовать как конфликт версии (HTTP 409) или отсутствие записи (404) после проверки.
- [ ] Запретить неявное изменение любых произвольных атрибутов через клиентский словарь updates; использовать allowlist и валидированные команды.
- [ ] Проверить остальные методы optimistic lock для Business, Service и значимых сущностей.
- [ ] Проверить, что миграция bookings_no_active_resource_overlap **применена на реальной PostgreSQL** и покрывает используемые статусы.
- [ ] Не заменять existing advisory locks / exclusion constraint одной только проверкой version.
- [ ] Написать тесты параллельного бронирования и параллельного обновления на PostgreSQL (не только SQLite).

**Приёмка:** недопустимые пересечения/потерянные изменения не воспроизводятся; конфликт возвращается без побочных эффектов.

**Gate 1:** массовое подключение бизнеса нельзя начинать до завершения SG-01–03.

## 5. Этап 2 — P1: PostgreSQL и вычисления BookingBot

**Приёмка:** соединения предсказуемы, не превышают бюджет, отказ PostgreSQL корректно диагностируется.

### SG-05 — запросы, индексы, календарь и CRM

- [ ] Использовать pg_stat_statements и EXPLAIN (ANALYZE, BUFFERS) для реальных горячих запросов на staging.
- [ ] Проверить существующие индексы и миграции; добавлять только необходимые composite/partial indexes.
- [ ] Перенести часть статистических агрегаций в SQL, избежать чтения всей истории в Python.

- [ ] Оптимизировать N+1-запросы, удерживая семантику услуг/ресурсов.
- [ ] Для больших индексов предусмотреть отдельную безопасную production-процедуру (например CREATE INDEX CONCURRENTLY там, где применимо).

**Приёмка:** на репрезентативном объёме данных меньше SQL/времени/памяти; нет регрессий календаря.

### SG-06 — быстрый расчёт свободного времени

- [ ] Пакетно получать выходные, мастеров и занятые интервалы для нужного диапазона.
- [ ] Убрать SQL из внутреннего цикла «каждый мастер × каждый слот».
- [ ] Сохранять поведение рабочих часов, интервалов, ночных смен, аренды и нескольких услуг.
- [ ] Кэш добавлять только при измеренной необходимости и наличии инвалидации после изменений.

**Приёмка:** число SQL-запросов не зависит линейно от произведения числа слотов и мастеров.

### SG-07 — воспроизводимые миграции

- [ ] Инвентаризировать папку migrations и автоматические ALTER TABLE в init_db().
- [ ] Сопоставить фактическую production-схему с моделью и историей миграций.
- [ ] Ввести единый версионированный процесс (Alembic допустим, но решение принимается по совместимости).
- [ ] Исключить немое подавление неизвестных ошибок DDL.
- [ ] Использовать совместимые схемы expand → migrate → contract и отдельный запуск миграций.

**Приёмка:** ошибка миграции видна и безопасно останавливает релиз; состояние БД воспроизводится.

- [ ] Измерить размер/рост чеков, фотографий, аудио и видео; проверить нагрузку на PostgreSQL/локальный диск.
- [ ] При необходимости использовать приватное объектное хранилище и lifecycle policy.
- [ ] Разделить временные рендеры и долговременные артефакты; при нескольких workers обеспечить общий доступ.
- [ ] Контроль прав на чтение файлов по business_id; нельзя выдавать чужие медиа через URL.

**Приёмка:** крупные медиа не перегружают критические API/БД и остаются доступны разрешённым работникам.

### SG-16a — SMENA, отдельный контур Telegram Serverless

- [ ] Проверить реальные лимиты Telegram Serverless/SQLite SDK, регистрацию смен, несколько организаций и фотоподтверждения.
- [ ] Нагрузочные и конкурентные тесты; корректность ежемесячного табеля и индексов.
- [ ] Проверить юрисдикцию данных, хранение фото и безопасную интеграцию с будущим кабинетом.
- [ ] Не переносить SMENA в общую инфраструктуру без подтверждённой необходимости.

**Приёмка:** известны пределы provider-hosted модуля и условия промышленной эксплуатации.

## 9. Этап 6 — наблюдаемость и тестирование

### SG-17 — метрики и восстановление

- [ ] p50/p95/p99, ошибки HTTP, RPS, медленные SQL, занятые соединения/блокировки.
- [ ] Queue depth, возраст самых старых заданий, job failure/retry/unknown, стоимость по компании.

- [ ] Correlation request_id/task_id/business_id; аудит без утечки персональных данных и ключей.
- [ ] Алерты по отказам, backup и периодический проверяемый restore.

**Приёмка:** по метрикам можно быстро найти источник ухудшения качества, а БД восстанавливается по инструкции.

### SG-18 — нагрузочные и аварийные испытания

- [ ] Сценарии: открытие календаря, поиск слотов, бронирование, перенос, отмена, аналитика и CRM.
- [ ] Гонки: один слот / много клиентов; два обновления с одной версией; истечение предоплаты во время оплаты.
- [ ] Совместная нагрузка: обычный Booking API + AI Growth OS (с моками платных вызовов).
- [ ] Нагрузочные ступени 10/50/100/250/500 VUs с заданными RPS, профилем действий и длительностью тестов.
- [ ] Повторить с большим объёмом исторических данных, а не только пустой базой.
- [ ] Fault injection: kill worker, API restart, DB disconnect, Telegram timeout, LLM timeout.
- [ ] Прогнать regression suites BookingBot и Growth OS; проверить сценарии смены/ночного времени.

**Приёмка:** документированы реальные limits, p95/error rate и отсутствие нарушения инвариантов. VUs ≠ подтверждённые одновременные пользователи или бизнесы.

## 10. Этап 7 — масштабирование по данным испытаний

- [ ] Несколько экземпляров Booking API за балансировщиком с health/readiness checks.
- [ ] Независимое увеличение числа безопасных Growth workers и notification workers.
- [ ] Управляемый бюджет DB pool и лимиты CPU/RAM.
- [ ] При необходимости отдельные ресурсы БД/медиа и CDN для статических данных.
- [ ] Redis/RabbitMQ/Temporal/Kubernetes/шардирование **только по подтверждённым требованиям**, не как обязательная часть первого релиза.

**Приёмка:** масштабирование улучшает фактические метрики без увеличения риска дублей/потерь.

## 13. Критерии окончательной готовности

1. Все protected API и инструменты агентов проверяют tenant/role и resource ownership.
2. Модели отображения слотов и записи совпадают, PostgreSQL защищает интервалы ресурсов.
3. Все критичные конкурентные изменения атомарны; потерянных записей нет.
4. Уведомления наблюдаемы, переживают рестарт и не выдают ошибку за успех.
5. Долгие AI-задачи безопасно захватываются, восстанавливаются и не повторяют оплаченные этапы без проверки.
6. Сайт бронирований работает независимо от тяжёлого видеорендера.
7. Изоляция файлов, расходов, почты и MCP между компаниями подтверждена.
8. Backup/restore, мониторинг и load/failure tests пройдены на согласованном целевом профиле.

**Ответственные:** назначить при создании отдельных issues. **Даты:** по результатам оценки трудоёмкости и production preflight; не обещать пропускную способность до нагрузочных тестов.
