# ServGo — план реализации единого MCP (перепроверенная редакция)

**Статус:** утверждаемый технический план, не реализация.  
**Дата ревизии:** 2026-10-30.  
**Базовый репозиторий для плана:** `grunvald91/booking_bot`.  
**Предполагаемый будущий сервис:** `grunvald91/servgo-mcp` (на дату ревизии репозиторий ещё не создан).  
**Предполагаемый публичный URL после запуска:** `https://mcp.servgo.ru/mcp` (пока не развёрнут).  
**Область:** BookingBot, CRM, AI Growth OS, ServGo Смена и почта.

> Этот документ — единая точка входа в реализацию. Галочки задач не означают, что код уже сделан. После создания `servgo-mcp` перенести сюда ссылку на каноническую спецификацию шлюза или перенести документ, оставив ссылку из BookingBot.

## 1. Цель, границы и архитектурные решения

Создать единый MCP-сервер ServGo, который позволяет разрешённым ИИ-клиентам (ChatGPT, Claude, внутреннему ИИ ServGo и другим) безопасно вызывать операции платформы. Вторая задача — возможность внутреннего ИИ подключать **внешние** MCP-серверы с отдельной политикой доверия и прав доступа.

**Принятые ограничения:**

1. **Один gateway, не единая база:** MCP Gateway не работает напрямую с БД модулей. Только защищённые адаптеры к доменным сервисам/API.
2. **Никакого выполнения SQL или произвольного кода через MCP.** Только явные версионированные инструменты с проверяемыми схемами.
3. **Источник идентичности — авторизация, не модель:** `user_id`, доверенный `business_id`, роль и область доступа устанавливаются после проверки токена и связи с бизнесом. Переданный агентом ID — лишь запрос на выбор из разрешённых бизнесов.
4. **Переиспользование правил:** сайт, Telegram, внутренний ИИ и MCP вызывают одинаковую бизнес-логику. Условия занятости слотов, предоплаты и уведомления не дублируются.
5. **Раздельные режимы:** публичная клиентская запись и кабинет владельца/сотрудника имеют разные permissions и наборы инструментов; административный доступ не возникает из обычной клиентской авторизации.
6. **Операции с побочными эффектами контролируются ServGo:** внешнее подтверждение в интерфейсе ИИ не заменяет серверные права, аудит, повторную проверку состояния и требуемое внутреннее подтверждение.
7. **Первый MVP — BookingBot.** CRM, Growth, Смена и почта не блокируют релиз первой версии.
8. **Без GitHub Actions по умолчанию:** тесты локально/в Codespaces; развёртывание через SSH. Соблюдать корневой `AGENTS.md`.

### 1.1 Схема потоков

```text
ChatGPT / Claude / external MCP client      ServGo internal AI
             |                                      |
             | OAuth / MCP                         | Internal policy
             v                                      v
       +-----------------------------------------------+
       |                  servgo-mcp                    |
       | MCPServer / Streamable HTTP / auth / policies |
       | tenant scope / validation / audit / approvals |
       +-----------------------------------------------+
             |              |            |         |
       Booking API       Growth API    Shifts API  Mail API
             |              |            |         |
       Booking domain    Dispatcher   SMENA domain Mail services
             |
       BookingBot + CRM

ServGo internal AI -> [separate MCP CLIENT + trusted server registry]
                    -> external MCP servers
```

Внутренний MCP-клиент не должен иметь неограниченных прав на вызов внешних инструментов.

## 3. Технические контракты

### 3.1 Протокол и SDK

- Целевая спецификация MCP: **2026-07-28**, плюс совместимость с клиентами предыдущей ревизии, которую предоставляет официальный Python SDK v2.
- Python SDK **v2**: импорт `MCPServer` из `mcp.server.mcpserver` (не `FastMCP` из v1).
- Транспорт: **Streamable HTTP**, TLS, стандартный endpoint `/mcp`; новые клиенты работают по stateless-протоколу, не хранить авторизацию в транспортной сессии.
- Выполнять требования к `Mcp-Method`, `Mcp-Name`, версии протокола, проверке `Origin`, защите от повторов и ограничению размеров запросов.
- Использовать структурированный `outputSchema`/результат инструмента и корректные аннотации инструментов (например, `readOnlyHint`, `destructiveHint`, `openWorldHint`). Аннотации **не заменяют** фактические permissions.
- Для долгих задач первая версия использует собственный сохранённый `operation_id` и инструмент проверки статуса. Стандартное Tasks extension добавлять только после проверки готовности SDK и клиентов, не блокировать MVP.
- MRTR можно поддержать для совместимых клиентов, но все критичные подтверждения должны работать без MRTR.

Источники: [MCP specification 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [Python SDK v2](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/whats-new.md), [Migration guide](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/migration.md), [SDK roadmap](https://github.com/modelcontextprotocol/python-sdk/blob/main/ROADMAP.md).

### 3.2 Авторизация

- Выбрать проверенный **OAuth 2.1 / OIDC** Authorization Server, привязать к аккаунту ServGo; **не** писать OAuth-сервер с нуля.
- Авторизация внешнего клиента: Authorization Code + PKCE, resource indicators/audience, scopes; поддержать **Client ID Metadata Documents (CIMD)** как приоритетный стандарт; DCR — только при необходимости для совместимости.
- Metadata discovery, проверка `iss` (RFC 9207), `aud`, `exp`, `nbf`, `scope`, отзыв выданных разрешений.
- Для внутренних API — отдельный доверенный сервисный credential с привязкой к gateway и безопасным способом передачи **проверенной** личности/организации; не пробрасывать клиентский OAuth-токен как универсальный секрет в каждый модуль.
- Решить, как актуализируются права без задержки: проверка членства/роли в бизнесе во время каждой операции с данными; запрет полагаться только на долгоживущий scope.
- Раздельные права для `owner`, `co-owner`, `administrator/staff`, `client`, сервисных агентов, с явной матрицей по инструментам.
- Подтверждение доступа к каждому бизнесу при выборе, включая строгую проверку связи Booking business ID ↔ Growth product ID ↔ SMENA org ID.

**Базовая матрица scopes:** `booking:read`, `booking:write`, `crm:read`, `crm:write`, `growth:read`, `growth:write`, `shifts:read`, `mail:draft`. Scope — необходимое, **но не достаточное** условие доступа. Отдельное разрешение на телефоны, email и другие персональные поля.

### 3.3 Стандартизованный результат инструмента

Вся операция возвращает либо структурированный успех, либо контролируемую ошибку. Пример доменного результата:

```json
{
  "ok": true,
  "operation_id": "op_...",
  "status": "completed",
  "business_id": 123,
  "data": {
    "booking_id": 456,
    "date": "2026-11-05",
    "time": "15:00"
  }
}
```

Возможные `status`: `prepared`, `awaiting_approval`, `running`, `completed`, `rejected`, `expired`, `failed`. Для ошибок использовать фиксированные коды: `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `APPROVAL_REQUIRED`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`. Не раскрывать SQL-исключения, токены, внутренние адреса.

## 5. Серверное подтверждение изменений

**Рекомендуемый сценарий:** `prepare → approve (если требуется) → commit → status`.

1. `prepare` создаёт неизменяемую запись предложения с `operation_id`, автором, business ID, нормализованным payload, версией/хэшем, сроком действия.
2. Если действие требует согласования, владелец видит заявку **в интерфейсе ServGo**, где отдельно аутентифицирован.
3. `approve` подтверждает именно указанное содержимое; нельзя подменить параметры между подготовкой и исполнением.
4. `commit` повторно проверяет актуальные права, содержимое заявки, прайс, доступность ресурса, срок действия и доменные ограничения, затем выполняет бизнес-операцию.
5. Дубли с одним idempotency key возвращают прежний статус/результат, а не повторяют side effect.
6. Падение процесса между коммитом и ответом клиенту не должно создавать новый результат при повторном запросе.
7. У операции есть явные статусы и ограниченное время хранения аудита согласно политике данных.

Примечание: MCP MRTR можно использовать как дополнительный UX-механизм, **но не как единственное основание** для подтверждения рискованных операций.

## 6. Тестирование и негативные сценарии

### P0 — обязательны для MVP

- [ ] Нет токена, поддельный/просроченный/отозванный токен → отказ.
- [ ] Подмена `user_id`, `business_id`, роли или scopes → отказ.
- [ ] Пользователь компании А пытается читать, менять или получить статус операции компании Б → отказ.
- [ ] Оператор без прав владельца выполняет административное изменение → отказ.
- [ ] Чтение расписания без явной проверки бизнес-прав → невозможно.
- [ ] Одновременное бронирование одного слота → один допустимый результат, второй конфликт.
- [ ] Повтор `booking_confirm` с тем же idempotency key → без дубликата.
- [ ] Изменение цены/занятости/прав после `prepare` → повторная проверка на `commit`.
- [ ] Повторная, истёкшая или чужая заявка на подтверждение → отказ.
- [ ] Сбой Telegram/email после commit → запись не пропадает, уведомление управляемо повторяется.
- [ ] Длинный диапазон дат, большие списки, массовые вызовы → квоты, пагинация, лимит данных.
- [ ] Логи/ошибки не раскрывают персональные данные, токены, DB-конфигурацию.
- [ ] Реальное подключение клиента v2 и совместимого предыдущего клиента → успешные вызовы по правилам их протоколов.

### P1/P2 — для следующих модулей

- [ ] Prompt injection в содержимом CRM, задач или ответов внешнего MCP не может инициировать действия.
- [ ] Соответствие организации SMENA проверено доверенным способом.
- [ ] Пользователь не получает зарплатные и персональные данные без отдельного права.
- [ ] Массовая рассылка/публикация требует preview, подтверждение, лимит и audit.
- [ ] Отмена/повтор задач Growth OS не теряет результат и учёт расходов.

## 7. Развёртывание, эксплуатация и откат

- Test/staging окружение с отдельной БД, OAuth-настройками и тестовым доменом.
- Отдельный публичный reverse proxy `mcp.servgo.ru` с TLS; backend API Booking/Growth/SMENA не публиковать без необходимости.
- Секреты — только через защищённые настройки сервера; ротация сервисных ключей, ограничение доступа, запрет записи токенов в логи.
- Health/readiness endpoints без персональных данных; метрики ошибок, задержек, количества запросов, конфликтов и отказов.
- Rate limiting на IP / пользователя / бизнес / client ID / инструмент; таймауты для upstream и лимит параллельных операций.
- Миграции схемы с резервной копией, тестом восстановления и обратимой процедурой переключения.
- Rollback приложения, возможность временно отключать отдельный инструмент или модуль без отключения всей платформы.
- Проверка headers, `Origin`, TLS, отказов, поведения при рестартах, сохранности аудита.
- Деплой **Codespaces + SSH**, без массового запуска GitHub Actions. Не включать автоматический деплой документационных веток.

## 10. Отложенные решения и блокеры

1. **Auth provider:** определить, существующая ли инфраструктура аккаунтов ServGo поддерживает все требования OAuth/OIDC, или нужно подключить отдельный готовый провайдер. До решения блокирует публичный доступ.
2. **Service-to-service identity:** выбрать способ безопасной передачи доверенного actor context из gateway в Booking API, не доверяя произвольным HTTP-полям.
3. **Канонические business links:** определить владельца справочника соответствий ID модулей, схему миграции и правила отзыва доступа.
4. **CRM:** убедиться, что ветка `feature/servgo-light-crm` не конфликтует с текущим `main`; проверить тесты перед объединением.
5. **Telegram Serverless:** проверить поддерживаемый доверенный доступ к SMENA; без этого не начинать интеграцию.
6. **Mail tenancy:** разделить права владельца платформы и владельцев предприятий до появления внешних mail-инструментов.
7. **Privacy:** согласовать сроки хранения аудита, минимизацию контактных/зарплатных данных и политику доступа.
