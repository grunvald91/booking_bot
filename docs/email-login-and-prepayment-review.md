# Вход без Telegram и проверка предоплат

Реализовано в коде; production выпуск выполняется отдельно после сверки исходников.

## Вход и права

`/login`: регистрация, вход по email/паролю и восстановление пароля. Новый пользователь
подтверждает почту шестизначным кодом и получает самостоятельный аккаунт без Telegram.
Код нужен при регистрации, привязке и восстановлении; обычный вход не отправляет
письма. Доставка использует существующий SMTP-модуль. Стоимость почты зависит от
провайдера; SMS-платежей здесь нет.

Уже вошедший владелец открывает «Настройки → Вход без Telegram» (`/account`),
подтверждает почту и устанавливает пароль. Это дополнительный вход в тот же `User.id`:
бизнесы и права сохраняются. Завершить привязку должен тот же авторизованный
пользователь, который запросил код.

«Настройки → Совладельцы → Добавить» принимает подтверждённый email зарегистрированного
пользователя. После нового входа пользователь получает существующие полные права
управления бизнесом без Telegram. Отдельной ограниченной финансовой роли нет.
Если единственный прежний владелец потерял доступ к аккаунту и Telegram, права
восстанавливает поддержка после проверки владения бизнесом. Регистрация сама по
себе не даёт прав на существующий бизнес.

Контактные `User.email` и телефон не доказывают владение аккаунтом. Вход использует
отдельную уникальную `email_identities`, созданную после подтверждения. Гостевые
записи не объединяются по совпадению номера/почты. Телефон без SMS — контактное
поле, не проверенный идентификатор. Обратное объединение двух уже созданных
аккаунтов email/Telegram этот патч не выполняет.

Пароли: индивидуальная соль и scrypt N=32768, r=8, p=3. Коды: только HMAC,
15 минут, максимум пять попыток, однократное использование. Подтверждение
аннулирует другие коды той же почты. Лимиты запросов и ошибок входа хранятся в SQL
и действуют между API-процессами. Восстановление пароля отзывает прежние email-JWT;
Telegram-вход остаётся отдельным способом доступа. Старый телефонный вход больше
не печатает коды в лог и возвращает ошибку при недоставленном Telegram-сообщении.

## Предоплаты

`/admin/prepayments`: выбранный бизнес, «На проверке», «Ожидают отправки», «Все
предоплаты», пагинация, контакты, услуги, дата и сумма. Обновление каждые 15 секунд;
после загрузки дополнительных страниц используйте «Обновить список». Карточка
расписания и Web Push о новой отправке оплаты ведут к проверке.

Чеки из сайта и новых Telegram-загрузок сохраняются в PostgreSQL до фиксации
`prepayment_sent`. Допустимы PDF/JPEG/PNG/WebP до 10 МБ, тип проверяется по содержимому.
HTML/SVG не принимаются. Файл доступен только авторизованным владельцам/совладельцам
этого бизнеса, с `no-store`, `nosniff`, `Content-Disposition: attachment`.
В браузере можно открыть изображение или скачать файл; публичных ссылок нет.
Старые чеки, пересланные только в Telegram, автоматически не импортируются — это
подписано в интерфейсе. Резервное копирование PostgreSQL включает новые файлы.

Сообщение клиента об оплате переводит весь последовательный визит в
`prepayment_sent` и останавливает автоотмену всех его услуг. Карточка проверки
показывает общую сумму за визит. Решение применяется ко всему визиту:

- «Подтвердить поступление»: после проверки денег владельцем `confirmed`, время
  подтверждения, аудит с автором.
- «Отклонить сообщение об оплате»: чек сохраняется, `pending_prepayment`, новое
  десятиминутное окно для проверки перевода/повторной отправки верного чека.
  Уведомление просит не платить повторно, если деньги уже списаны.
- «Отменить бронь»: отдельная операция `cancelled`, освобождение ресурса. Перевод
  клиент → бизнес проходит вне ServGo; изменение статуса не возвращает деньги.

Общий `database/prepayment.py` используется вебом и ботом. SQL-блокировки визита
и версии защищают от одновременно принятых решений и старых кнопок. Новые
Telegram-уведомления включают версию; старые кнопки сохраняют совместимость.
Старый PATCH статуса также проверяет предоплату и аудирует подтверждение/отмену:
нельзя завершить неоплаченную запись или обойти ожидание сменой на `pending`.
Нулевая предоплата не запускает таймер; истёкшая неоплаченная бронь не восстанавливается.

## Настройка и выпуск

1. Сверить production-файлы согласно `CLAUDE.md`. Сохранить копии изменяемых
   файлов и frontend build, проверить резервное копирование базы. Не копировать
   репозиторий целиком.
2. До старта новых API/бота применить `migrations/add_email_auth_and_payment_review.sql`:
   только пять новых таблиц/индексы, без изменения владельцев, броней и цен.
   Для всего PR также нужны прежние миграции из `servgo-sales-agent.md`.
3. Задать API `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM_EMAIL`, при необходимости
   `SMTP_USERNAME/SMTP_PASSWORD`. Для 587 — STARTTLS, для 465 — SSL. Настроить
   SPF/DKIM и проверить доставку тестовому адресату. Задать разные случайные
   `JWT_SECRET` и `SERVGO_EMAIL_AUTH_SECRET`, каждый минимум 32 символа. Без SMTP
   или сильных секретов email-вход отключён. Смена JWT_SECRET завершает прежние
   браузерные сессии. За proxy настроить доверенные адреса для корректного IP
   ограничения; не доверять произвольному `X-Forwarded-For` от клиента.
4. Доставить согласованные версии:
   `database/{models,crud,prepayment,receipts}.py`,
   `web/api/{deps,main,schemas}.py`,
   `web/api/routes/{auth,email_auth,payments,admin,client}.py`,
   `bot/handlers/{admin,client}.py`, `bot/keyboards/admin_kb.py`,
   `bot/services/{notification_events,email_notifications,webpush}.py`.
   Новый frontend build из `App.tsx`, `api/client.ts`, `authUtils.ts`,
   `components/{EmailAuthForm,AdminShell,Layout}.tsx`,
   `pages/client/{AccountPage,LoginPage,BookingStatusPage}.tsx`,
   `pages/admin/{PrepaymentsPage,SettingsPage,SchedulePage}.tsx`.
5. Перезапустить web API (сверить фактическое имя службы) и `booking-bot`.
   Проверить `/api/health`, `/api/auth/email/capabilities`, регистрацию/привязку,
   восстановление, сохранение прав владельца. В demo-бизнесе проверить чек через
   сайт/бот, запрет чужому владельцу, подтверждение/отклонение/отмену, уведомления
   и освобождение слота. Сам чек не доказывает получение денег.

Откат: согласованные предыдущие API/бот/frontend и перезапуск обеих служб. Новые
таблицы/чеки оставить для сохранности истории. Старый API убирает email-вход и
веб-проверку: пользователям только с email потребуется поддержка. Не возвращать
слабый JWT_SECRET ради старых сессий. Сохранить совместимый expiry worker, пока
не закончатся ранее установленные окна, как описано в `servgo-sales-agent.md`.
Массовое изменение статусов и удаление броней не требуется.

## Проверки

`tests/test_email_auth_and_payments.py`: отдельные UUID-схемы PostgreSQL,
синтетические данные, подменённые SMTP/Telegram. Проверяются права, вход/привязка,
отзыв JWT, коды/лимиты, конкурентная проверка кода, приватные чеки, общие веб/бот
переходы, версии решений, визиты, отмена, пагинация и повторяемость миграции.
